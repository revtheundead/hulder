# D1 cost on the L4 (Phase 3)

What in-server probe placement costs on the serving path, for D1 (docs/design.md §5). Four arms are served in turn on one GPU, over three rounds, each arm-run a fresh `vllm serve`: a baseline with no probe, B with the stock `ExampleHiddenStatesConnector` (`b_stock`), B with a connector that skips its disk write (`b_noop`), and vllm-lens 1.3.0 in eager mode scoring a linear probe (`lens`). The arm order rotates each round. The run decides cost only. Getting a score out before tokens stream is D3's question.

Modal L4 (Ada, 24 GB, driver 610.57.04), 4 CPU, 32 GiB, vLLM 0.30.0, vllm-lens 1.3.0, torch 2.13.0. Qwen3-4B at `1cfa9a72` in bf16, probe layer 18, `--max-model-len 2048`, chunked prefill on, prefix caching off, CUDA graphs on except for lens. Each arm-run checks 16 greedy replies of 64 tokens, runs a saturation bench of 300 prompts, then a fixed-rate bench for 75 s at 14.22 req/s, 70% of round 0's baseline saturation. Every bench reply is 128 tokens. Records are in [`modal/20261031T151758Z/`](modal/20261031T151758Z/), and the server and bench logs stayed local. Estimated cost $1.44, 4,174 s of container time.

Reproduce from the repository root, the run at `4648fdce7aab` and the rejudged verdicts at `fdb1b5a9b3a9`:

```bash
uv run --with modal==1.6.1 modal run experiments/phase3/d1_modal.py --spent-usd 0.0
source scripts/dev-env.sh && uv run python experiments/phase3/d1_l4.py --rejudge docs/results/phase3/modal/20261031T151758Z/d1_l4.json
```

## Verdicts

**B fails the cost rule on throughput, and lens fails it by not sustaining the fixed rate.** The run completed all 12 arm-runs without a stop rule firing.

The rule passes an arm when its worst round's overhead against that round's baseline is at most 5% for saturation throughput and 10% for fixed-rate p99 TTFT and p99 TPOT. It has two readings here, because the rule was changed after seeing this run's data.

| Arm | As run (`d1_l4.json`) | Rejudged (`verdicts_rejudged.json`) |
|---|---|---|
| `b_stock` | None. Throughput inconclusive, both latencies fail | False. All three metrics fail |
| `b_noop` | None. Throughput inconclusive, both latencies fail | False. All three metrics fail |
| `lens` | False. Did not sustain the fixed rate in any round | False, unchanged |

As run, a metric was inconclusive whenever the baseline's own range across rounds exceeded half its threshold, and any inconclusive metric left the arm undecided even beside a failing one. The baseline's throughput ranged 2.64% across rounds, just over half of 5%, so B's throughput was inconclusive at about 40%, roughly 15 times that range.

**The revised rule was decided after seeing the data.** A metric now fails when its smallest overhead across rounds exceeds the threshold plus the baseline's range, whatever the noise check says, and an arm fails on any failing metric. The first reading is the rule as set before the run. The second isn't, so treat it as a judgement on this run rather than a preregistered result. The case for it is that no amount of baseline noise at 2.64% explains a 39.5% minimum.

## Throughput

Saturation throughput, 300 prompts, in requests per second. Overhead is the paired drop against the same round's baseline.

| Round | Baseline | `b_stock` | `b_noop` | `lens` |
|---|---|---|---|---|
| 0 | 20.31 | 11.93 (41.3%) | 12.03 (40.8%) | 4.91 (75.8%) |
| 1 | 19.85 | 11.93 (39.9%) | 12.18 (38.6%) | 4.95 (75.1%) |
| 2 | 19.79 | 11.97 (39.5%) | 11.88 (40.0%) | 4.89 (75.3%) |

The threshold plus the baseline's range is 7.64%. B's smallest overhead is 39.5% for `b_stock` and 38.6% for `b_noop`.

**The disk write isn't B's cost.** `b_noop` writes nothing and loses as much as `b_stock`, within a round's noise. Whatever costs B about 40% is in the extraction path itself, and the draft token below is the one candidate the counters show. That attribution is not measured.

## Latency, which doesn't count for B

| Round | Baseline p99 TTFT / TPOT (ms) | `b_stock` | `b_noop` |
|---|---|---|---|
| 0 | 196 / 52.4 | 475 / 137.8 | 450 / 136.6 |
| 1 | 201 / 53.0 | 437 / 131.7 | 449 / 135.9 |
| 2 | 201 / 52.8 | 461 / 137.4 | 464 / 136.7 |

These are overheads of 118% to 142% on p99 TTFT and 148% to 163% on p99 TPOT, and the rule as run failed both. **They measure B overloaded, not B's latency cost.** The fixed rate of 14.22 req/s is 70% of the baseline's saturation but 117% to 120% of B's own (11.88 to 12.18). B finished each 1,066-request bench at 12.4 req/s, its saturation, in 86 s against the baseline's 80 s, with up to 260 to 273 requests in flight against the baseline's 123. So the latencies here are queueing above capacity. B's verdict rests on throughput alone, which holds without them. A latency comparison needs a fixed rate every arm can sustain.

## Greedy replies

Each arm-run's 16 greedy replies are compared with round 0's baseline. A divergence counts once per prompt, at its first differing token, and is classed by the baseline's top-two logprob margin there, as an exact tie at 0, within bound up to the tie bound of 0.25, or a change above it.

| Arm-runs | Exact tie | Within bound | Change |
|---|---|---|---|
| `b_stock`, each of 3 | 2 | 3 | 0 |
| `b_noop`, each of 3 | 2 | 3 | 0 |
| `lens`, each of 3 | 3 | 2 | 0 |
| Baseline, rounds 1 and 2 | 0 | 0 | 0 |

The divergences are the same prompts at the same tokens in every round, so they're deterministic, as in the local check (`d1_local.md`). B and `b_noop` diverge identically.

**Prompt 13 sits at the edge of the bound.** In all six B arm-runs, prompt 13 diverges at token 59 (`" wait"` in the baseline, `" since"` in B), where the baseline's margin is 0.24999994, one float32 step below 0.25. It counts as within bound only because the bound is 0.25. The bound was reasoned from bf16 rounding of logits between 16 and 32 (two bf16 steps of 0.125), not measured on this GPU. So this one prompt depends on the tie bound being exactly that value, and a bound a hair lower would have called it a change in every B arm-run and fired the generation stop rule. The other within-bound divergences sit at 0.125, one step.

## Decode waste

From each server's `/metrics`, summed over the greedy check and both benches. Every arm scheduled 201,310 tokens, but `vllm:iteration_tokens_total` counts prompt tokens and accepted output tokens only, so it hides B's drafts.

| Arm | Steps | Draft tokens | Accepted |
|---|---|---|---|
| Baseline | 1,917 to 1,928 | 0 | 0 |
| `b_stock` | 1,161 to 1,216 | 173,436 to 173,440 | 42 to 46 |
| `b_noop` | 1,160 to 1,168 | 173,434 to 173,438 | 46 to 48 |

**B drafts one token per request on every decode step and almost always has it rejected.** The 173,438 drafts are within 1% of the run's decode steps per request (175,872 output tokens less one per request), and 0.03% are accepted. The drafter proposes the token just sampled as the next one, so a draft is accepted only when the model repeats a token. The local check saw 0 of 63 accepted. B takes fewer steps than the baseline because it is slower, so more requests share each step.

## KV cache and concurrency

| Arm | KV-cache tokens | Max concurrency at 2,048 | Peak running |
|---|---|---|---|
| Baseline | 86,768 | 42.37× | 256 |
| `b_stock` | 74,944 in round 0, then 83,984 | 36.59×, then 41.01× | 256 |
| `b_noop` | 83,984 | 41.01× | 256 |

B's 83,984 is 3.2% below the baseline, close to the 3.4% one layer's hidden state should take per token (5,120 bytes against 147,456 for Qwen3-4B's KV). `b_stock`'s smaller round 0 cache came with its cold compile, and the cause isn't pinned down. Every arm peaked at vLLM's default 256 running requests during the saturation bench, so concurrency didn't differ there.

## Where this falls short

- One GPU, one model, one sequence length and one output length. B's 40% is for 128-token replies at 256 running requests. Its cost at lighter load isn't measured.
- B's latency at a rate it can sustain isn't measured, and nor is lens's.
- The revised rule was chosen after seeing this data (above).
- The cause of B's throughput loss isn't separated. The draft token is the leading candidate, not a measured one.
- Lens's cost isn't split between eager mode and its hook.
- Prompt 13's divergence passes on a tie bound that was reasoned, not measured.
